# YBER — prototype v0.1

Boat and yacht rentals first; the rest of marina life (slips, fuel, service, crew) layered onto the same account later.

## Run it

Requires Node 18 or newer. The app itself has no dependencies; `npm install` only fetches the test runner.

```
npm install
npm start          # builds index.html, then serves http://localhost:3000
```

Data persists to `data/db.json`, seeded from `src/seed.json` on first boot. `npm run reset` wipes it.
The page detects the server (`/api/health`) and uses the API; opened directly as a file (after `npm run build`),
it falls back to an in-browser store instead.

Demo login: `demo@yber.app` / `demo1234` (has past and upcoming trips, 1,450 Sea Miles).

## Test it

```
npx playwright install chromium    # once per machine
npm test                           # every flow, in both modes
npm run test:ui                    # same, with a window showing each step
```

`npm test` runs each test twice: against `index.html` opened as a file, and against `server.js` started on
port 3100 with a throwaway database. It never touches `data/db.json`. GitHub runs the same suite on every
pull request (`.github/workflows/tests.yml`).

Working with others: see [CONTRIBUTING.md](CONTRIBUTING.md). Using Claude Code: it reads [CLAUDE.md](CLAUDE.md).

## What is real and what is simulated

| Area | Status |
|---|---|
| Landing, region picker, search, filters, sort, wishlist | Real, client-side |
| Listings, accounts, bookings, listings you publish | Real when served by `server.js` (JSON on disk); in-browser otherwise |
| Price quote (rate × days + optional captain + 12% fee) | Real, identical formula client and server (`YBER_RULES.quote` / `RULES.quote`) |
| Sea Miles, levels, badges, streak | Real, awarded server-side |
| Payment | Simulated (no card capture). Stripe is the next integration |
| Photos | Uploads work (stored as data URLs, max 6 × 2.5 MB). Illustrations are generated SVG until a listing has photos |
| Map | Schematic SVG placeholder with price pins. Needs Mapbox/Google + real coordinates |
| Auth | Prototype only: plain-text passwords, bearer token = user id. Replace before any real user touches it |
| Marinas page | Teaser with mock data; the search form only shows a toast |

  api.js            data layer: same method surface for in-browser and server modes

Edit anything in `src/`, run `npm run build` (or restart `npm start`), reload. `src/seed.json` is the only copy of the seed data: the server reads it directly, and the build embeds it into `index.html` for no-server mode.

## API (server mode)

```
GET   /api/health
GET   /api/regions                     → regions with live listing counts
GET   /api/listings?region=miami
GET   /api/listings/:id
POST  /api/listings                    auth   → { listing, gain, user }
POST  /api/auth/signup                        → { user, gain, token }
POST  /api/auth/login                         → { user, token }
GET   /api/me                          auth
PATCH /api/me                          auth   { name }
GET   /api/me/listings                 auth
GET   /api/bookings                    auth
POST  /api/bookings                    auth   { listingId, from, to, captain } → { booking, gain, user }
POST  /api/bookings/:id/cancel         auth
POST  /api/wishlist/:id                auth   → { wishlist, gain, user }
```
`auth` = `Authorization: Bearer <token>`. Errors return `{ error }` with a 4xx status.

## Design references, and what was taken from each

- **Duolingo** (landing + onboarding): 70px nav with only a logo and a language pill, one illustration + one headline + two stacked buttons, a scrolling strip under the fold, alternating feature blocks with lowercase coloured headings, a full-bleed coloured CTA. Button physics (4px bottom shadow that collapses on press), the green progress bar with the highlight stripe, and the card grid on the region step. Colours and mascot are YBER's own.
- **Turo** (search): rounded search pill with Where / From / Until / Guests, a row of filter pills with popovers, results on the left in a 2-column card grid (image, name, rating + trips, host badge, price per day + est. total), sticky map with price pins on the right.
- **Dockwa** (account + marinas): Trips / Profile structure, boat details saved to the profile, the slip-search form shape and per-foot-per-night pricing.
- **DockMaster** (roadmap): the marina-operator side (slip maps, service, fuel, billing) listed as the "all-in-one" modules.

## Suggested next steps, in order

1. Postgres + Prisma (or SQLite for speed) replacing `db.json`; hash passwords, real sessions.
2. Stripe Checkout on the confirm step; hold funds until trip start.
3. Mapbox GL in `MapSVG()` with real lat/lng on listings and marinas.
4. Availability calendar per listing so double-booking is impossible.
5. Object storage (S3/R2) for photos, replacing data URLs.
6. Messaging between guest and host (Dockwa's most-used feature).
7. Marinas module: slip inventory, LOA/draft on the profile, request-to-book.
